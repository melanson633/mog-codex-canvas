Mog Canvas — Functional Uses and Experience Design

Grounding Context

Mog Canvas embeds a real WASM-backed spreadsheet engine (@mog-sdk/spreadsheet-app) inside an AI agent's chat surface via MCP and the MCP Apps UI extension. Seven model-facing tools exist: list_workbooks, open_workbook, get_workbook_session, save_workbook, validate_workbook, screenshot_workbook, close_workbook_session.

Two lanes write one file. The human lane is the live canvas, running editModel: { user: 'write', agents: 'none', automation: 'none' } — agent edits in the canvas are forbidden by policy, not convention. The agent lane is the headless SDK. The handoff rule ("save before switching lanes") is social and unenforced.

Identity is content-derived. A workbook's revision is the SHA-256 of its bytes on disk. The save pipeline stages, fsyncs, backs up to .bak, then atomically renames. A stale save is refused with a 409 and the loser's bytes are preserved as .conflict-<stamp>.xlsx — nothing merges silently, and concurrency was measured rather than assumed. The fingerprint is total: it answers "are these the same bytes?" perfectly and "which cells moved?" not at all.

Composition beat forking. The shipped compare view is ~50 lines of static HTML that mounts 2–3 full app instances in iframes driven by URL flags (?wb=, ?compact=1, left/mid/right, layout=vertical). Because each pane is the whole app, each keeps Save/Verify/Screenshot and per-file revision protection for free. Each pane is also a full engine runtime (~41 MB WASM), so panes are for human-scale comparison, not dashboards.

Constraints every idea was qualified against: one security policy across browser, headless, and MCP surfaces (workbook-root containment, canonical realpath(), no absolute or UNC paths, no NTFS alternate data streams); workbook bytes never travel over HTTP; the dev server must serve the page (a file:// origin silently yields blank iframes, and the engine's WASM is answered at two URL shapes); Vite must not watch the workbook root (EBUSY kills the server mid-save on Windows); and no claim of Codex host support without passing the host-acceptance gate.

What the SDK type surface actually exposes

The original run could not check this — node_modules was absent from the ideation worktree and the verifier had no network. It is installed in the primary worktree, and reading @mog-sdk/contracts and @mog-sdk/sdk settled three questions that the ranking below turns on.

The dependency graph is queryable. worksheet.d.ts declares four overloads returning plain A1 address lists:

/** Get cells that depend on this cell by A1 address. */ getDependents(address: string): Promise<string[]>; getDependents(row: number, col: number): Promise<string[]>; /** Get cells that this cell depends on by A1 address. */ getPrecedents(address: string): Promise<string[]>; getPrecedents(row: number, col: number): Promise<string[]>;

This is data, not the UI trace-arrow command (TRACE_DEPENDENTS exists separately as a UIActionType). A recalc engine must maintain this graph to function at all; the SDK simply hands it over. Cascade tracing therefore requires no formula parser and no graph construction.

The volatile-function blind spot is already named. contracts/versioning declares FormulaDependencyClosure carrying rootFormulaObjectIds, dependencyObjectIds, and a boolean includesVolatileFunctions. INDIRECT/OFFSET build references at calculation time, so no static trace can follow them — the SDK's own model expects a closure to declare when it is incomplete rather than present a clean-looking graph with silent holes.

SDK version history will not persist to disk. sdk/version-store.d.ts supports memory, memory-durable-snapshot, indexeddb, and browser. Every filesystem kind — node-file, filesystem, node:fs, fs — is enumerated in MOG_SDK_UNSUPPORTED_VERSION_STORE_KINDS, with a comment stating the shape is public so callers "get an explicit unsupported diagnostic instead of an implicit memory fallback." Durable cross-session change history has to be ours.

Verification status These are the shipped published type declarations, read from the installed package. No call has been executed against a live workbook. Confirming getDependents() returns what it declares, on a real file, is the first task before anything is built on it.

Settled Direction

The original ranking was produced without the workbook owner's input. Three answers reordered it, and they are recorded here because they are not recoverable from the code.

Settled with the owner — 2026-08-04

1. What "what changed?" must look like. Not a cell list. A dependency cascade: assumption cell (old → new) → dependent (old → new) → dependent (old → new), plus an accumulating dataset of all changes for distilling lineage and cascade patterns over time.

2. No approval gate. Agent changes apply automatically. The single exception is a cell the user currently occupies. Review-and-accept workflows are explicitly rejected as a bottleneck.

3. Multi-pane comparison has no real use case. The compare view was built as a deliberate stress test of the embedding model, not to serve a comparison workflow.

Answers 1 and 2 are coupled, and that coupling is the most consequential thing in this document. Auto-apply without a gate is only safe because the cascade record exists afterward. Remove the trace and the same policy becomes invisible mutation with no audit path; keep it and no gate is needed, because the system has a flight recorder instead of a checkpoint. Answer 1 is the price of answer 2.

Answer 2 also promotes what looked like a UX nicety into a safety interlock. "Unless the user is in that cell" requires the canvas to report its cursor outward. Nothing in the adapter interface does that today. That wire is no longer optional decoration; it is the mechanism that makes gate-free auto-apply survivable.

Answer 3 retires axis C. Cross-pane coherence, the blink comparator, and pane-addresses-a-revision all lose their motivation at once.

1

The previous revision is already on disk — make it addressable

Description. Every successful save copies the prior file to <name>.xlsx.bak before the atomic rename. That is a free, byte-perfect previous revision, written on every single save. And the path policy makes it unreadable: every requested path must end in .xlsx, so nothing in the system — canvas, MCP tool, or headless lane — can ever open it. The project pays for versioning on every write and cannot spend it.

The fix is a naming and addressing change, not a policy loosening: give path-policy.ts a typed artifact-kind namespace (deliverable, backup, conflict, ledger) instead of a two-entry extension map. Containment, realpath() resolution, null-byte and ADS rejection all stay exactly as they are.

This ranks first on leverage rather than visibility. Four otherwise-separate candidates collide on the same two lines: diff-against-previous, the ledger's storage target, conflict-file review, and revision addressing. One typed namespace unblocks all four. Most importantly, it is where every old value in idea 2's cascade comes from.

Downsides
Expands the set of writable/readable path kinds, which is exactly the surface the containment policy exists to keep small. It must be a closed enum with per-kind rules, never a relaxed extension check. .bak is also only ever one revision deep — this is not history, it is the immediately previous state.

2

Trace the cascade, not the diff

Description. The unmet need across this whole category is "what did it change?", and the default answer everyone builds is a cell-by-cell diff. For a model with formulas that answer is nearly useless: two hundred cells changed, and the reader still has to reconstruct why. The useful artifact is the cascade — one assumption moved, here is the blast radius, in dependency order, with old and new values at each hop.

The reason this is not expensive is that the engine already owns the graph and exposes it as getDependents() / getPrecedents(). The work decomposes into three parts, and two are close to free:

ComponentSourceCost
Which cells changed (the seed set)The agent wrote them — it does not need to rediscover its own edits by comparing filesFree
The cascade from each seedgetDependents(), walked breadth-firstOne call per hop
Old value at each cell in the cascadeThe .bak, read at those addresses onlyIdea 1 + a targeted lookup

Note what this avoids: no full-workbook comparison, no XLSX parsing, no formula parser, no graph construction. You compute the affected set first — typically dozens of cells — and then look up exactly those addresses in the previous revision.

What makes the trace worth reading is dependency depth, not formula count. An earlier draft of this idea claimed the cost curve inverts the usual one — that the more formulas a workbook has, the more useful the trace. That is false, and a counterexample settles it: a workbook with 12,340 formulas and zero cross-sheet references traces exactly one hop. Every seed's dependents are its immediate neighbours and the cascade terminates there; the output is a flat list, which is the diff this idea exists to avoid. Formula count sets the width of a layer. Only depth — chained precedents, cross-sheet references, calculated columns feeding other calculated columns — produces the causal ordering that makes a cascade more legible than a diff.

So the honest scoping is narrower and more useful: this idea earns its keep on deep models, and a shallow-but-wide workbook should be expected to produce a one-hop trace. That is worth knowing up front rather than discovering after building it, and it suggests measuring depth on real target workbooks before committing to the feature. The falsification and the general practice it motivated are recorded in docs/solutions/design-patterns/validate-workbook-feature-designs-against-a-second-genre.md.

Cascades from a widely-used assumption can also be large enough to need summarizing, and the accumulated dataset needs idea 3 to have anywhere durable to live.

3

The change ledger — durable, because the SDK's is not

Description. Three lanes write these files — the canvas, the MCP tools, the headless SDK — and not one of them signs its work. SaveResult carries no actor. SessionState carries no actor. The SHA-256 proves the bytes are intact and says nothing about who produced them. "The file changed" should be able to become "the agent changed it at 2:04, from revision a3f…, in response to turn 7."

This was ranked seventh as an audit nicety. Two things moved it up. First, the owner's requirement for "a dataset of all changes" to distill lineage and cascade patterns over time — that dataset is precisely a ledger, and idea 2 produces its rows. Second, the SDK will not host it: every filesystem version-store kind is explicitly enumerated as unsupported, deliberately, so that callers get a loud diagnostic rather than a silent in-memory store that evaporates when the process exits. Durable cross-session history is ours to build or it does not exist.

Axis
B — change legibility
Basis

codesdk/version-store.d.ts — MOG_SDK_SUPPORTED_VERSION_STORE_KINDS is memory/indexeddb/browser only; node-file, filesystem, node:fs, fs all sit in the unsupported list with an explicit "no implicit memory fallback" rationale.

codeworkbook-service.ts — SaveResult and SessionState carry no actor or lane field; the same service serves all three lanes.

ownerSettled direction, answer 1: an accumulating dataset of all changes is part of the requirement, not an extra.

Rationale
Idea 2 answers "what did this one change do?" The ledger answers "what has been done to this model, by whom, in what order" — and it is the only thing that makes cascade patterns (as opposed to single traces) computable. Under a no-approval policy it is also the entire accountability story.
Downsides
A ledger is durable state with its own growth, corruption, and concurrency questions, and it must live inside the same containment policy as everything else — which is another reason idea 1 comes first. Append-only keeps it simple but unbounded; anything smarter needs a compaction story.
confidence 85% complexity medium depends on 1
4

The canvas→host uplink as a collision interlock

Description. Information flows one way today. The host mounts the canvas, passes it options, and hears nothing back about what the user is doing inside it. There is no selection event, no cursor event, no viewport event in the adapter interface — the only callback is onDirtyChange, and it updates a local wrapper element rather than signaling outward.

The original run ranked this third as an input-surface idea: highlight a range, and the selection becomes the prompt scope. The verifier refuted the cheap framing — an earlier draft claimed an existing dirty-state uplink precedent, which was a miscitation — and the owner's second answer then changed what the wire is for. Auto-apply "unless the user is in that cell" cannot be implemented without the canvas reporting cursor position outward. The uplink is no longer a convenience; it is the interlock that makes gate-free auto-apply survivable.

Selection-scoped prompting remains its first and best consumer, and the same channel later carries viewport and staleness. But it must be built as new plumbing, not discovered as existing plumbing.

Rationale

5

Refresh quietly on inSync — no bottleneck

Description. get_workbook_session computes inSync: current.revision === session.revision — correctly — and nothing in src/ ever reads it. The staleness signal exists and has zero consumers. The user therefore discovers that the agent changed the file at the moment their own save is refused, having already worked on bytes that no longer exist.

The original framing was an andon cord: detect staleness, stop the line, make the human acknowledge. The owner rejected bottlenecks outright, so the behavior inverts — reload quietly, and interrupt only when unsaved edits would actually be destroyed. Checking at focus and visibility boundaries is not a compromise here but the only viable design: Vite must not watch the workbook root, because watching a file mid-save throws EBUSY and kills the dev server on Windows.

A — agent↔canvas signaling
Basis

codeserver/mcp/mog-canvas-server.ts — get_workbook_session returns inSync; grep across src/ returns zero consumers.

codevite.config.ts — the workbook root is explicitly excluded from watching, for a documented EBUSY failure.

ownerSettled direction, answer 2: no gates, no bottlenecks.

Rationale
Cheapest correctness win in the set — the detection logic is already written and already right; only the consumer is missing. Under auto-apply it is also what keeps the human's view honest without ever asking them for permission.
Downsides
A silent reload discards in-flight unsaved edits and disturbs scroll and selection, which is the exact failure the feature exists to prevent — so "quiet" must still mean "quiet unless the canvas is dirty." Focus-boundary checks are also inherently late: a change made while the tab is focused is not noticed until focus is lost and regained.

6

Chrome is already a declared API; the CSS reach-in should go to zero

Description. The adapter already passes the embed a structured chrome object — { commandBar, fileMenu, formulaBar, sheetTabs, statusBar } — with every value hardcoded. Compact mode ignores it entirely and instead hides the same elements by reaching into the vendor's own DOM with unversioned Tailwind-utility selectors. Two mechanisms exist for one job, and the fragile one is doing the work. There is no version guard, no feature detection, and no test asserting the selectors still match after an SDK upgrade.

This was the run's strongest consensus — 5/5 agents, independently re-verified. It drops to sixth only because the settled direction promoted three change-legibility items above it, not because anything weakened. It remains the lowest-complexity item here and the only one with a visible payoff: in a 302px pane, visible grid goes from 0px to roughly 213px.

Live defect, not a proposal

Compact mode hides the app footer (.app.compact .foot { display: none; }), and the footer is where adapter-failure warnings render. So in small panes and the compare view — precisely where a degraded or stub canvas is hardest to notice — the warning that says the real engine did not load is the part that gets suppressed. This is a one-line fix and needs no ideation.

codesrc/styles.css — .app.compact .canvas .mog-spreadsheet-app-theme-scope > .shrink-0.border-b:first-child and the matching border-t:last-child rule target the vendor's ribbon and status bar by utility class.

Rationale
Deletes a version-fragile coupling, replaces it with the supported interface, and turns a single on/off flag into a real density dial — which is what any future display-mode work (thumbnail, working pane, full editor) would need anyway.
Downsides

7

Open-with-intent: let the agent aim the canvas

Description. open_workbook accepts exactly { name: z.string() }. When the agent opens the canvas for the user, the only thing it can communicate is which file — not where to look, and not why the canvas appeared at all. The user reconstructs intent from chat scrollback.

Two optional fields close it: a range to scroll to and select, and a one-line reason to display. It is the mirror image of idea 4 — there, the human points at cells to instruct the agent; here, the agent points at cells to direct the human. It also gains value from idea 2: a cascade result is far more useful when the canvas can open already aimed at the seed cell.

Axis
A — agent↔canvas signaling
Basis

codeserver/mcp/mog-canvas-server.ts — the open_workbook inputSchema is a single required name string.

codesrc/App.tsx — ?wb= is validated against the config file list, establishing the pattern any new parameter should follow.

Rationale
Small, self-contained, and it makes every other idea's output land somewhere useful. Low risk: both fields are optional and additive, and the existing validation pattern already exists to copy.
Downsides
A range is a claim about a workbook the agent may not have re-read, so a bad or stale range aims the user at the wrong place with full confidence. The reason string is also model-authored text rendered in the app's own chrome, which needs the same escaping discipline as any untrusted input.
confidence 85% complexity low

Rejection Summary

Thirteen candidates did not survive as standalone ideas. Rejection here means "not a separate unit of work" — several were absorbed rather than discarded.

CandidateDisposition
Genlock / shared-view endpoint Cut on owner direction. Ranked sixth before the owner confirmed the compare view is a functionality stress test with no comparison workflow behind it. Scroll-locking panes solves a problem nobody has.
Blink comparator Cut with genlock. Flicker-based change detection needs aligned panes and same-workbook addressing; the verifier also found the "zero diff infrastructure" claim overstated, since it silently depended on two other candidates.
Pane addresses a revision Cut with genlock. Its remaining value — reading a previous revision — is delivered by idea 1 without any pane involvement.
0 MB receipt pane Cut with genlock.
Review-and-accept workflow Cut on owner direction. Explicitly rejected as a bottleneck. Auto-apply is the settled policy; accountability moves to ideas 2 and 3 after the fact.
Positive control transfer (explicit lane handoff) Deferred. It is an enforcement-policy decision about who may write when, not a build — and it points the same direction the owner just ruled out.
Change-pack over validate/screenshot output Folded into ideas 1 and 2. It was the cheap approximation of the cascade; the real graph API makes it unnecessary as a separate step, though it remains a fine fallback for non-formula changes.
Typed artifact-kind namespace Folded into idea 1 — it is the mechanism, not a separate proposal.
Conflict inbox Downstream of idea 1. Once .conflict-<stamp>.xlsx is addressable, reviewing one is an application of the cascade rather than new infrastructure.
Pre-flight staleness claim Folded into ideas 1 and 5.
Contract proof / signed deliverable Overlaps ideas 1 and 3 almost entirely; the ledger carries the provenance without a second artifact format.
Selection-as-prompt as a standalone quick win Refuted by the verifier and re-scoped into idea 4. No selection event exists in the adapter, and the "existing dirty-state uplink" that made it look cheap was a miscitation.
Control sheet (a sheet that drives the agent) A product fork rather than an improvement to this one. Better handled as a brainstorm variant if it is ever wanted.

Unverified Claims

Stated plainly so nothing here is mistaken for established fact:

  • All SDK findings are read from published type declarations in the installed package. No call has been executed against a live workbook. getDependents() returning what it declares is the first thing to confirm.
  • External prior art referenced in the grounding — Paradigm's column-prompt model, Excel Agent Mode's formula-emission behavior, the Rows shutdown, blink-comparator history, broadcast genlock practice — was not re-verified in this run and had no network access available to check.
